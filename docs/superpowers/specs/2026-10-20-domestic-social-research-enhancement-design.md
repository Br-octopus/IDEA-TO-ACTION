## 2. 现状与必须先处理的问题

最初实现使用了独立工作树，其代码版本早于 D 盘主工作树。不得整目录覆盖；逐项把已审查的社媒改动整合进 D 盘当前代码，并保护其中现有写作/PPT 未提交改动。后续实现、委派、构建和应用验收均以 D 盘主工作树为准。

目前已有四平台搜索适配、Electron 独立会话、计划确认、预算、报告和历史研究入口。它们是已有实现，不代表四个平台已经真实验收通过。现有详情、评论、字幕尚未形成可用闭环。

第一阶段先处理已发现的问题：

- 平台卡片渲染路径使用了作用域内不存在的 `task`，可能导致运行时报错。
- 浏览器已打开、是否登录、搜索能否使用，目前容易被压缩为同一个 `ready`，造成错误阻断或错误显示可用。
- 检查真实搜索链接，避免误将作者主页作为微博帖子，补齐知乎回答与文章的域名和链接类型识别。
- Reddit、YouTube 历史任务保持可查看；禁止新建和重新执行同时落实到界面与协调器。
- 当前四平台保持待实测，完成实际应用环境验收后才逐项开放能力。

## 3. 产品目标和边界

保留“单研究 Agent + 多平台工具 + 确定性工作流”。模型负责计划与分析；应用代码负责权限、调用、预算、队列、错误分类和恢复，不让模型自行选择任意命令或工具。

支持两种研究输入：

- 输入主题：确认研究计划后搜索，再选择候选内容深入读取。
- 粘贴平台内容链接：识别平台和内容 ID，确认读取范围后直接研究，免去重复搜索。

四种研究模板继续保留：趋势与热点、用户痛点与口碑、内容与竞品研究、事实与方案核查。输出同时包含结构化报告和可追溯原始结果集。

首批只读，不发布、点赞、评论、关注或发送私信；验证码和二次验证交给用户。不增加代理池、账号轮换和自动验证码处理。媒体文件不默认下载；正文、截图、字幕原文等附件由用户选择保存。

本轮不扩大到抖音、快手、贴吧、微信公众号，不引入多 Agent 运行体系、数据库、向量索引或通用插件市场。

## 4. 连接与采集结构

### 4.1 保留现有结构，加入受控采集入口

```text
研究输入 → 用户确认计划与预算 → 研究协调器
                                 ↓
                    按平台、具体能力选择连接
                       ├─ 应用浏览器页面适配
                       ├─ MediaCrawler 本地采集进程
                       ├─ 已登记的可选 MCP 服务
                       └─ 已登记的平台 API
                                 ↓
                  标准化、去重、覆盖度与来源记录
                                 ↓
                 报告与原始结果集 → 用户选择保存
```

沿用现有 Electron 主进程、IPC、本地 Node 服务和前端模块。新增本地进程管理和采集桥接职责即可，不重建通用 Agent 框架。

平台 API 是数据访问方式，MCP 是工具连接协议。MCP 后端可能仍使用网页或非官方接口，不能因为连接类型为 MCP 就视为官方 API。每个来源同时记录连接类型与实际采集方式。

### 4.2 基于 MediaCrawler 修改的范围

在项目内保留固定版本的源码副本和自有桥接代码，先复用四个平台所需的搜索、内容详情、有限评论、结果字段、登录检查和采集节流。其他平台、媒体下载、代理池和无关 WebUI 不进入本轮产品运行路径。

运行时使用专用 Python 虚拟环境及锁定依赖，不修改系统 Python 配置。Node 及浏览器依赖由环境检查明确识别；不能假设 Electron 自带的运行环境可以直接供外部脚本使用。源码置于应用资源内，实际可写运行环境、会话和运行数据置于应用用户数据目录。

Electron 通过本地子进程桥接发出固定动作，桥接层调用复用后的采集代码并返回结构化事件；研究 Agent 不直接操作 MediaCrawler 命令行。请求、结果、进度、错误均包含任务与操作标识；日志走独立通道并脱敏，不能混入结果协议。

采集动作按调用交付结果，避免启动一次搜索就附带抓取所有正文、评论和媒体。应用层预算必须传入并在采集进程内再次执行，不能只在界面显示上限。

导入清单记录上游仓库、实际提交、文件列表、本地修改和依赖。后续更新先检查这些修改与结果协议的兼容性，再切换使用版本；不能直接用上游最新分支覆盖。

### 4.3 浏览器及登录态归属

现有 Electron 浏览器继续承担可视化页面访问、登录和可见内容读取。MediaCrawler 所需的自动化浏览器由应用另行管理，通过独立 profile 启动；它与 Electron 窗口不是天然共享会话。

界面明确显示当前来源对应的浏览器和登录状态。两个进程不得同时写同一个 profile，也不默认导入用户日常浏览器目录或静默交换 Cookie。用户在实际使用的浏览器完成登录；会话失效仅暂停依赖该会话的能力。

如果采集引擎需要 Chrome/Edge，环境检查提供可执行文件位置和缺失说明。优先启动应用专用 profile，不自动接管用户日常浏览器。外部浏览器退出时仅清理本应用拥有的进程与连接。

### 4.4 可选 MCP 的职责

MCP 用于补充已验证的能力和替代来源，不要求每个平台重复安装一个 MCP。小红书详情、评论优先评估裁剪后的 MediaCrawler 能力；B 站字幕单独评估 MCP 的可获取性，不假定 MediaCrawler 已提供字幕。

首批候选包括 `xpzouying/xiaohongshu-mcp`、`XZXZZX-Ai/bilibili-mcp`；它们是待接入验证的候选，不在设计阶段宣称全部可用。只登记所需的搜索、详情、评论和字幕工具，其他工具不暴露给研究模型。

#### B 站字幕候选锁定评估（阶段二后续接入）

阶段二候选锁定为 [`XZXZZX-Ai/bilibili-mcp` v1.14.3](https://github.com/XZXZZX-Ai/bilibili-mcp/releases/tag/v1.14.3)：Apache-2.0，要求 Node.js >=20，发布清单含 12 个工具。当前唯一允许评估接入的只读工具为 `get_video_transcript`，其参数和返回字段以[官方工具参考](https://github.com/XZXZZX-Ai/bilibili-mcp/blob/master/docs/tool-reference.md)为准。锁定候选不代表已登记、已安装或可用；来源登记、安装和生命周期由 Task7 完成。

接入时必须显式设置 `force_asr=false`、`fallback_to_asr=false`、`fallback_to_description=false`，并校验返回的 `data_source`。只有可验证为平台字幕的结果才能标记为字幕；`data_source` 未知时记录为 `unknown`，不得推断语言、人工/自动字幕类型，也不得把本地 ASR 或视频简介当作平台字幕。仅接收具有可验证时间戳的字幕分段；缺少或无效时间戳的条目不得伪装成带时间轴的字幕。未登记该来源时，B 站字幕能力在 UI 中始终显示不可用且禁用。

工具白名单只限制应用发起哪些调用，不等于对子进程实现了系统级隔离。因此只支持经过评估的固定项目、专用目录和最少环境变量，不把任意仓库安装包装成安全能力。

## 5. 能力、状态和连接选择

### 5.1 分开表示状态

每个来源分别记录：

- 运行状态：未安装、检查中、运行中、停止、异常。
- 浏览器状态：未打开、启动中、已打开、关闭、冲突。
- 登录状态：已登录、未登录、过期、未知、等待人工验证。
- 各项能力：未实现、待验证、可用、受限、异常。
- 实现版本、最近检查时间和最近实际成功时间。

公开搜索是否需要登录由具体来源和实际页面判断，不能固定写成整个平台永远无需登录。浏览器打开或登录成功均不能代替真实搜索检查。没有执行真实检查时不能更新“最近成功时间”。

能力分为搜索、详情、评论、二级回复、字幕、截图、创作者内容；后续能力单列，不用一个总开关代表全部可用。

### 5.2 自动选择与手动指定

默认自动选择，也允许用户指定应用浏览器、MediaCrawler、已配置 MCP 或已配置 API。仅显示当前平台实际登记的选项。既有 `auto/api/browser` 数据保持兼容，新增模式通过状态迁移引入，不改坏旧报告。

自动模式按具体能力选择已配置、最近验证可用的来源。四平台初始以应用浏览器搜索为基础，深入读取优先使用已验证的 MediaCrawler 或 MCP；同能力存在正式 API 时优先使用已配置且满足范围的正式 API。用户手动指定时不静默改用其他来源。

进程异常、网络超时、能力不支持或字段缺失时，最多切换一次可用来源。成功但零结果作为正常空结果处理；只有计划明确的覆盖度不足且预算允许时才补搜，不能用“必须找到若干条”无限搜索。

同一平台、账号或共享上游出现限流、验证码、账号受限时，对相关来源统一暂停，不通过切换来源连续重试。不同来源的浏览器登录不自动互认。

每次切换记录原因、来源、操作和预算消耗。去重使用平台与内容 ID，缺少 ID 才使用规范化链接；不同来源取得的同一内容合并来源记录。内容指纹仅用于标记相似内容，不能误合并不同用户的评论或独立证据。

## 6. 分平台交付与后续优化

| 平台 | 本轮交付目标 | 写入路线图的后续优化 | 开放前提 |
| --- | --- | --- | --- |
| 小红书 | 搜索、正文详情、有限一级评论 | 二级回复、创作者公开内容与主页研究 | 回复层级、翻页和计数可控；创作者范围单独确认 |
| 哔哩哔哩 | 搜索、视频详情、有限一级评论、可获取字幕 | 弹幕、本地语音转写、章节分析 | 弹幕有数量和时间范围；转写依赖、下载范围、时长和存储明确 |
| 微博 | 搜索、帖子详情、有限一级评论 | 热点检索、热点变化跟踪 | 明确热搜来源、抓取时间及跟踪频率，不把榜单当全站趋势 |
| 知乎 | 搜索、回答正文、文章正文 | 评论、问题下多回答比较 | 区分问题、回答和文章，记录实际覆盖的回答范围 |

路线图能力属于正式设计范围，但不自动纳入四阶段的当前验收。各能力在完成来源评估、预算扩展、会话检查和真实验证后单独开放。

抖音、快手、贴吧、微信公众号作为后续平台候选，评估搜索来源、公开范围、用户授权、运行依赖和维护成本后再立阶段，不因 MediaCrawler 已覆盖就自动出现在新建研究中。

未来仅在角色职责和并行任务确实增加、单 Agent 的分析与采集协调形成瓶颈时，提示用户评估拆分多 Agent；本轮保持单 Agent。

## 7. 研究流程、预算和用户控制

### 7.1 先广搜，再按需深入

流程为：输入主题或链接 → 生成计划 → 用户确认 → 准备检查 → 搜索或解析链接 → 用户选择深入内容 → 获取已选详情、评论或字幕 → 分析 → 报告 → 选择保存。

选择深入内容时展示实际调用项与剩余预算。计划中已批准的选中内容可以直接执行；新增平台、扩大时间范围、超预算或新增未批准的采集类型时，只确认变化部分。

### 7.2 初始预算

| 项目 | 新任务初始值 | 计量范围 |
| --- | --- | --- |
| 平台数量 | 最多 4 个 | 整个任务 |
| 每平台查询 | 最多 3 个 | 含补充查询 |
| 搜索结果 | 每平台最多 20 条唯一内容 | 搜索页摘要，不附带全量正文 |
| 搜索翻页 | 每查询最多 2 页 | 同时受总调用与时间限制 |
| 深入内容 | 全任务最多 10 条 | 粘贴链接同样计入 |
| 一级评论 | 每条内容最多 20 条 | 全任务最多 200 条；不自动取二级回复 |
| 字幕 | 最多 3 个视频，合计媒体时长最多 60 分钟 | 仅选中视频；不默认转写或下载音视频 |
| 来源调用 | 全任务最多 100 次 | 包括失败、重试、分页和切换产生的出站请求 |
| 自动采集时间 | 最多 10 分钟 | 含请求和节流等待，不含人工登录与暂停等待 |
| 模型分析量 | 最多 10000 token | 计划、报告和重生成共用额度；超过时停止后续模型请求 |
| 主动保存附件 | 合计最多 25 MiB | 正文、截图、字幕及其他已选附件 |

这些是可调整的产品默认值，不代表各平台承诺可获取的数量。连接检查搜索和诊断请求也记录消耗；任务开始后进行的检查计入该任务预算。来源内部分页及重试必须能计量；不能提供计量和停止支持的来源，不进入自动深入采集流程。

模型返回 token usage 时按返回值累计；未返回时，以输入 UTF-8 字节数加请求开销估算，并以输出文本字节数和 `max_tokens` 上限中较小值估算输出。模型请求的 `max_tokens` 不超过剩余额度扣除输入估算后的部分。超时且无法获知实际用量时预留剩余额度；计划请求失败则保留默认计划、错误说明和已计用量供用户确认。界面区分模型报告用量与估算用量。

每平台、每 profile 同时最多一个采集动作，先采用串行队列。节流遵循来源要求和服务端等待提示，不用随机等待宣称能够避免限制。达到任一预算后停止新增动作并保留已有结果。

## 8. 统一结果与研究报告

搜索结果延续链接、标题、作者、发布时间、采集时间、摘要、查询词、公开指标、证据状态和附件索引；增加以下可追溯字段：

- 平台内容 ID、内容类型、规范化 URL、内容版本或指纹。
- 来源 ID、采集引擎/适配版本、连接类型、页面读取或接口采集方式。
- 采集动作、成功或失败状态、实际覆盖范围、是否截断及截断原因。
- 详情正文与来源摘要分开；失败时不能用摘要冒充完整正文。
- 评论 ID、父评论 ID、排序方式、实际取得数量及可见总数（来源提供时）。
- 字幕语言、平台字幕/人工字幕/自动字幕/本地转写的来源类型（能识别时），以及分段起止时间；无法判断则标为未知。
- 材料 ID 与报告引用关系；视频分 P 和字幕所属分段需要明确对应。

错误区分正常空结果、内容不存在、访问权限不足、字幕不存在、字幕不可访问、登录过期、限流、人工验证、环境异常、超时和页面结构变化。不能把所有失败都转成空数组。

报告包含核心发现、平台共同点与差异、代表性材料、冲突与反例、未完成范围、待核验事项和后续建议。每条结论关联实际取得的材料；评论排序、样本数量和截断范围在报告中可见。

热门评论、搜索排序和少量样本不能直接代表全体用户。跨平台重复搬运不能算独立佐证；观点、广告表达与事实分开，证据不足时直接说明。

模型外发仍经过既有发送预览，只传研究所需摘要和用户选择的片段；平台正文、评论中的指令作为待分析数据，不得修改工具权限或研究计划。报告引用也不得自动加载任意外部地址。

## 9. 安装、配置、更新与回退

### 9.1 第二阶段提供最小运行闭环

小红书和 B 站深度能力首次接通前，必须已经具备来源登记、依赖检查、专用环境初始化、启动/停止、超时终止、固定版本和明确错误反馈。第二阶段允许通过应用内基础连接配置及环境检查入口完成准备，不要求先做完第三阶段全部安装管理界面。

### 9.2 第三阶段完成可维护体验

平台连接管理提供安装、配置、检查、启动、停止、修复、查看脱敏日志、检查更新、升级、回退和卸载。只管理固定清单中的来源；自定义 MCP 的一般接入留作后续评估。

安装状态包含未安装、检查环境、准备依赖、安装中、验证中、可用和失败。安装前显示下载来源、版本、所需依赖和运行目录；缺少依赖时就地说明并提供应用范围内的准备动作，避免只给一段命令让用户自行排查。

更新流程：检查版本 → 用户发起升级 → 准备独立候选环境 → 验证协议与工具清单 → 检查与当前平台能力的兼容性 → 无运行任务时切换 → 保留上一可用版本。不得在研究中途升级或修改 profile。

候选失败保留旧版本。新版本首次运行失败且属于版本兼容问题时可回退并告知；登录过期、限流、字幕不存在不作为自动回退理由。旧环境有明确数量和清理入口，卸载不默认删除用户登录态或已保存材料。

外部 MCP 与 MediaCrawler 运行环境支持独立版本管理；第一版应用浏览器适配随应用升级，连接管理显示适配版本和最近验证时间。高频变化时再评估带校验与回退的独立适配更新包，不直接远程加载任意脚本。

## 10. 任务暂停、取消和恢复

### 10.1 操作级进度

任务记录计划版本、操作 ID、平台、来源、能力、内容 ID、查询与分页游标、已用预算，以及等待、运行、完成、失败、跳过状态。操作完成后持久化摘要与进度，不只依赖页面内存。

暂停停止分配新操作；在途请求在超时内结束，结果仍可入账。取消停止新操作并发出取消信号，超时后只终止应用拥有的采集进程；已完成结果保留，在取消生效后返回的未完成结果丢弃，调用消耗仍计入预算。取消后不自动生成报告，用户可以选择基于已有材料整理报告。

### 10.2 重启和备份恢复

应用重启后任务显示等待恢复，不自动联网。恢复前检查配置、来源版本、登录状态和预算；将中断的在途操作标为结果未知，由用户选择重试或跳过。重试沿用原操作关联并记录新尝试，不清零预算，也不重复计入已确认的唯一结果。

第三方分页游标可能失效。失效时从已知内容集合开始受预算控制地重新查询并去重，不能保证返回完全相同的排序。任务不保证恰好一次执行，但应避免重复持久化已完成材料。

未选择长期保存的正文和字幕只在内存临时分析；重启后只恢复摘要和完成记录，需要重新分析全文时明确提示重新获取并消耗剩余预算。用户已主动保存的正文可从本地附件恢复，避免为断点恢复偷偷长期保存全部原文。

## 11. 凭证、存储和备份边界

轻量计划、摘要、报告和操作进度继续使用现有工作区状态。完整正文、截图、字幕等主动保存的附件使用现有附件存储，索引只保存 ID、类型、大小、来源材料、相对路径和保存时间。

应用管理的显式凭证沿用 Electron 安全存储。第三方会话目录、Cookie 文件和 profile 不因此自动具备相同加密保证；按实际存储方式显示说明，限制于应用专用用户目录，不将它们交给模型、前端普通状态、报告、日志或备份。

备份包含任务计划、摘要、报告、选择、进度和已保存附件；排除凭证、profile、采集进程、可执行环境、本机绝对路径和未保存原文。来源配置只备份非敏感的来源标识与版本期望，不备份命令、环境变量或 Cookie。

恢复到另一台设备后，来源显示待安装或待检查；历史成功记录只作为历史信息展示。不得把备份中的“可用”直接作为当前可用状态。

## 12. 四阶段交付及验收

### 阶段一：四平台搜索与浏览器状态做稳

范围：修复已知运行时问题，分离状态，校验链接与去重，强化历史兼容和来源日志；先完成应用浏览器的真实搜索闭环。

验收：四平台分别验证正常搜索、正常零结果、登录要求、页面不支持、窗口关闭、暂停与取消、重启后的待检查状态；登录态不会相互混淆，历史任务不能重新运行。未通过真实验证的能力继续显示待实测。

### 阶段二：接入小红书、B 站深度能力

范围：基于已授权 MediaCrawler 代码裁剪并建立本地进程桥接，交付最小环境准备和生命周期管理；小红书接正文与有限评论，B 站接详情、有限评论及经过验证的字幕来源。补充链接直读、预算计量和证据字段。

验收：选中内容后才触发深度读取；源内分页、评论上限及取消实际生效；两个采集入口不能并发占用同一 profile；缺失正文、字幕不存在和字幕访问失败有不同显示；浏览器与 MCP 的会话不被误认为相同；报告能返回对应正文、评论或字幕时间点。

### 阶段三：完善安装更新和任务恢复

范围：在阶段二最小管理能力上补完整安装、修复、升级、回退界面；接入持久化操作队列、重启恢复、预算延续和备份迁移。

验收：全新用户目录可准备已登记来源；安装中断可恢复或清理；失败升级保留旧环境；研究运行时不能切换版本；重启不自动抓取，恢复不清零预算；取消保留完成结果；备份不夹带凭证或运行环境。

### 阶段四：扩展微博、知乎深度能力

范围：沿用同一桥接、预算和维护方式，微博补帖子详情和有限评论，知乎补回答与文章正文。

验收：微博结果指向实际帖子；知乎正确区分问题、回答、文章及对应域名；正文与搜索摘要分开；单平台失败不阻断其他平台；连接和深度材料的保存行为与前两平台一致。

所有阶段均检查状态迁移、预算边界、来源切换、结果规范化、备份清洗和实际界面调用路径。实现验证以项目现有脚本和有价值的专项检查为准，按执行时用户的验证授权运行，不把设计中的验收条目写成已通过结果。

每个实际实现任务按用户已选的子代理流程进行“实现 → 规格审查 → 质量审查”，委派包含完整工作树路径。真实平台验收与本地检查结果分开记录；未完成真实验收时，不用本地检查通过宣称平台稳定。

## 13. 后续优化的推进条件

- 二级回复：先扩展父子关系、去重和独立回复预算，再开放给用户选择。
- 创作者研究：先增加明确的创作者列表和时间范围，避免无边界抓取主页全部内容。
- B 站弹幕：先定义时间覆盖、数量上限、去重和样本偏差，再接入报告。
- 本地转写：单独按需安装，用户确认音频获取、时长、模型与本地资源预算后执行；不假装它是平台原生字幕。
- 热点跟踪：另行确认运行频率、变化阈值和停止条件后实施，本轮不创建定时任务。
- 知乎多回答比较：按指定问题与回答数量执行，报告注明未覆盖全部回答。
- 新平台、远程适配更新、通用 MCP 接入和多 Agent：分别评估收益与维护成本后立项，不能作为四阶段的隐含工作。
